# Roadmap

Work tracking for `omni`. This is a live document — add to it freely, clean it up as items land or get rethought.

- **Next** — work identified for the next release, grouped under the version it ships in.
- **Backlog** — work we intend to do but haven't pinned to a release.
- **Ideas** — scrappy reminders that aren't fleshed out enough to be backlog items yet.

---

## Next

### v2.0.0

Landed: providers as data, the Decisions API, the Mistral, Together, xAI and TypeSafe providers, thinking replay on Completions providers, thinking across models, and `thinking: true` as `:medium`. The design as built is in `design.md`; every user-facing change is logged in `context/notes/v2-changes.md`. Left before release:

- **Docs polish** — A style and polish pass over moduledocs and the README, after the accuracy pass that closed the Decisions API. Model loading has no user-facing docs beyond `providers:`: `config :omni, :models` `source`, `filter` and `transform`, and switching dialects (the two steps and the on-your-own warning, in `design.md`); perhaps an extras page on configuring providers and loading, filtering and transforming models. Settle the tagline (README, `Omni` moduledoc) and the `mix.exs` package description, which still read "Streaming text generation, tool use, and structured output" and leave out decisions.
- **Review `thinking: true`** — It is now an alias for `:medium`, which is less clear than writing `:medium`. Decide whether to keep it, give it a meaning of its own ("on, at the model's default"), or drop it and accept only levels and `false`. `design.md` (thinking, "Not adopted: a dynamic mode") has why it became `:medium`: with no level sent, users got the provider's default on some models and Omni's on others. Whatever is chosen, update the Text generation guide (Thinking) and the upgrade guide ("`thinking: true` means `:medium`"). Module docs that say it too: the `:thinking` option under `Omni.stream_text/3`, and the Thinking section of `Omni.Dialect.Text` ("`true` is `:medium`"). `Omni.Model`'s `thinking: true` is the model field, a different thing, and stays.
- **Upgrade guide and changelog** — Before release, turn `context/notes/v2-changes.md` (the running log of every user-facing v2 change) into an "Upgrading to v2" extras page in the docs, and write a concise `CHANGELOG.md` entry covering the broad areas of change, pointing to the guide. Each v2 phase adds to the log as it lands.
- **Release checklist** — Refresh the snapshot (`mix omni.snapshot`, golden test expectations), run the sweep over the matrix, bump the version in `mix.exs` (still 1.6.5).

## Backlog

- **Decision hosts awaiting catalog data** — Hosts that serve System One but have no `type: decision` models in models.dev, so no built-in loads them (a module adds capabilities to catalog models; it never adds models to a provider the catalog knows). Ollama Cloud (`https://ollama.com/v1/systemone`, `clef:cloud`); Alibaba (a per-workspace host, `https://{WorkspaceId}.ap-southeast-1.maas.aliyuncs.com/compatible-mode/v1/systemone`, `decision-model-preview`, 16 questions max, same key as chat, so an endpoint on `:alibaba` the user sets under `dialects:`); Venice (`/api/v1/systemone`, `jev-latest`, `clef`, `clef-api`). Upstream: a TypeSafe entry in models.dev, and a way for a catalog to say `gpt-6-luna` serves two APIs. Not built-ins: Cloudflare (wraps responses in `{result}`), Vercel, nano-gpt, vivgrid, melious.
- **Decision confidence** — Hosts compute confidence differently (TypeSafe from the top probability, Ollama and others from entropy, OpenAI unspecified), and Omni passes it through. Computing one formula from the probabilities would make it portable; no one has asked.
- **Gemini Interactions dialect** — Google's Interactions API (`POST /v1beta/interactions`, model in the body) has been GA since 2026-06 and is its "primary" API; `generateContent` is "legacy" but fully supported, with no sunset and mainline models still landing there. Deferred until a model or use case needs it: every Google chat model is on both, the only Interactions-only models are the Deep Research agents and non-chat models, and what it adds (server-side state, background runs, managed agents) is what a stateless library doesn't use. Only Google and Vertex serve it; OpenCode Zen and Go (an undocumented `/interactions` route aside), ofox and OpenRouter don't, so `GoogleGenerateContent` stays either way. ai-sdk, LiteLLM, pi and req_llm default to `generateContent`; ai-sdk and LiteLLM offer Interactions as an opt-in. When built: `google_interactions` / `Omni.Dialects.GoogleInteractions`; `store: false` on every request (the default stores interactions for 55 days) with the full history as steps; thought steps carry the signatures and go back exactly as received; SSE `interaction.*` and `step.start`/`step.delta`/`step.stop` events; the stop reason comes from `status` (`completed`, `incomplete`, `requires_action`); function results keyed by `call_id`; `response_format` for structured output; lowercase schema types. models.dev v1 can't route to it (`@ai-sdk/google` means `generateContent`); its experimental v2 data lists `interactions` per model, so until a source reads that, the Google provider declares a second endpoint and users move models with `transform:`.
- **Per-endpoint auth and headers** — Auth, headers and the API key live on the provider. If a gateway ever needs either per dialect, the field joins `Omni.Provider.Endpoint` and overrides the provider's. Nothing needs it yet.

- **DeepSeek provider and the empty reasoning fill** — DeepSeek V4 documents a 400 when, with `tools` in the request, an assistant message lacks `reasoning_content` ("must be passed back… even for turns where the model did not perform a tool call"), which a turn from another model now always does. No gateway reproduced it (Zen, Together and OpenRouter accepted the field absent, mid tool loop and with tools present), so the fill is unverified. A built-in DeepSeek provider (none today; the catalog provider loads with no replay flag) is the place to prove it. The fill can be generic: `""` and `" "` on every assistant message without the field did no harm on Zen and Together DeepSeek, Kimi K3 (Moonshot, Together), GLM-5.3, Qwen3.8 (Alibaba, Venice) and gpt-oss on Groq. ai-sdk and pi send `""`, LiteLLM `" "`. Kimi didn't need it.
- **Warning mechanism** — Some providers silently drop unsupported features (e.g. Ollama skips URL-based image attachments; OpenAI Decisions has no field for predicate criteria; some System One hosts drop choice descriptions). Need a consistent way to surface these gaps to users — options include Logger warnings, a warnings list on Response, or warning events in the stream. Compat `omit` gives it the message for free ("this provider ignores `:cache`"), as does `thinking: false` on a model that can't switch off.
- **Mistral tool call ids** — Mistral rejects tool call ids that aren't 9 characters of a-z, A-Z, 0-9 (`"Tool call id was ... but must be a-z, A-Z, 0-9, with a length of 9"`, mistral-vibe#1075), so a history from another provider (`toolu_...`, `call_...`) fails there. GLM models on Mistral reportedly emit `chatcmpl-tool-...` ids (pi #8387), which may fail on their own next turn; unverified, as the free tier serves no GLM. The fix is a reshape flag that rewrites non-conforming ids to a deterministic 9-character hash on encode (pi does this); prove it with one verify run carrying a foreign id.
- **Mistral PDF input** — Mistral takes PDFs over Chat Completions as `{"type": "document_url", "document_url": "https://..." | "data:application/pdf;base64,..."}` parts (its `file` part takes only an uploaded `file_id`). The catalog lists no PDF input on any Mistral model, so it needs a new `attachment_format` value plus `models/2` adding `:pdf` (as Venice does). Additive, so not needed for v2.0.
- **Together's DeepSeek V4 Pro thinks with `thinking: false`** — Found by the sweep (`no_thinking` fails). The catalog gives `DeepSeek-V4-Pro-0813` a toggle, and Omni sends `reasoning: {enabled: false}` as Together documents for hybrid models (pi and LiteLLM do the same), but it still reasons. Untried: `chat_template_kwargs: {thinking: false}`, which Together's reasoning docs list as an alternative toggle. If that works, it is module code for this model; if nothing does, the catalog's toggle is wrong.
- **Claude thinking-off data** — Anthropic's thinking-type table (2026-10) settles the old "Opus 5.5 thinks with `thinking: false`" item: Opus 5.5, Fable 5 and 5.1 and Mythos reject `disabled` with a 400, so no toggle is right and the sweep already skips `no_thinking` on Opus 5.5. Two gaps remain, both data, not Omni: Opus 5 takes `disabled` (at `high` effort or below) but the catalog gives it no toggle, so `thinking: false` sends nothing and it thinks; still missing in the 2026-10-28 models.dev data, left to the catalog to fix. Sonnet 5.5 rejects `disabled` but takes `thinking.type: "between_tools"` (no up-front thinking, at `high` effort or below), and ai-sdk maps `'none'` to it there. Unsupported until catalog data can say a model takes it and similar adapters agree on how it maps.
- **Candidate compat flags** — Seen in prior art (Pi, Vercel, LiteLLM, req_llm); each ships only with a built-in provider that needs it (the ship rule in `design.md`).
  - Anthropic Messages (Fireworks' and OpenRouter's Anthropic endpoints, MiniMax): empty thinking signatures allowed; no `cache_control` on tools; no eager tool-input streaming; temperature unsupported; adaptive thinking forced.
  - OpenAI Responses (OpenRouter): no long cache retention; no developer role; `store: true` rejected. xAI needed none of these.
  - Completions: a forced-tool `output_format` (Groq, Fireworks, req_llm's default).
  - A stateful parse hook for reasoning streamed inline as `<think>` tags (req_llm does this for Groq).
- **Unverified live** — Built-in behaviour not yet run against the live API, for lack of account access:
  - NearAI entirely (no key; wire output unchanged since phase 1), including its two catalog decision models over System One at `https://cloud-api.near.ai/v1/systemone`, an endpoint NEAR AI doesn't document. Its fixtures were recorded on `zai-org/GLM-5.1-FP8`, since dropped from the catalog, and replay on `z-ai/glm-5.3`.
  - OpenCode Zen's `/inference/` mounts (`openai/v1`, `anthropic/v1`, `google/v1beta`), which the refreshed catalog uses instead of `zen/v1`; fixtures were recorded on `zen/v1`. The sweep covers them.
  - Mistral's reasoning models on its own API (`mistral-small-2603`, `mistral-medium-2604`: 429 on the free tier, which serves them nothing) and GLM on Mistral (`zai-glm-5-3`: 403, not in the tier). Thinking chunks and their replay passed through OpenCode Zen's `mistral-large-4`, which passes Mistral's wire through; the sweep runs that model, and only Ministral on Mistral itself.
  - Groq Qwen: the `"default"` effort and `reasoning_format: "parsed"` (paid plans closed to sign-ups).
  - Ollama Cloud string levels on models other than gpt-oss (`glm-5.3`, `kimi-k3`; paid plan). `glm-5.2` reports an off switch the catalog lacks, so off sends nothing there. `deepseek-v4-flash`, `minimax-m3` and `mistral-large-4` report no thinking values at all.
  - Alibaba's budget-only thinking shape (`qwen3-next-80b-a3b-thinking` isn't served on the international endpoint).
  - Accepted as imperfect: Opus 4.5 and 4.6 use budget thinking rather than adaptive since the prefix lists went.

## Ideas

- **OpenRouter models API as a data source** — `https://openrouter.ai/api/v1/models` carries per-model reasoning data (`supported_efforts`, `mandatory`, `default_effort`) and per-endpoint `supported_parameters`, which llm_db drops. Could feed `Model.thinking` for OpenRouter more precisely than models.dev.
- **Reasoning tokens in `Usage`** — Most APIs report how many output tokens went on reasoning (Completions `completion_tokens_details.reasoning_tokens`, passed through by OpenRouter; Gemini `thoughtsTokenCount`; Responses `output_tokens_details.reasoning_tokens`); Anthropic doesn't. Omni drops the count. It's billed as output, so users may want it; it would also let verify tell "thinking was on" from "the model reasoned".
- **Align source filtering** — ModelsDev drops deprecated models; LLMDB keeps deprecated and drops retired. Pick one rule.
- **Audio and video modalities** — models.dev has these columns but they are currently filtered out in `Model.new/1`. Needs investigation into encoding requirements and provider support before adding `:audio` and `:video` to `@supported_modalities[:input]`. The per-capability dialect shape from the Decisions API work opens the door; no current need, so low priority.
